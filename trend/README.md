# AI Trend Search (마케터용 주간 AI 트렌드 뉴스레터)

- 최신 호(탭 2개): **주간 뉴스레터** `trend/index.html`(Pages `/trend/`) + **마케터 자료** `trend/marketer.html`
- 오늘의 AI 뉴스 탭: `trend/news.html` ← `trend/data/news.json`. 매일 07:00 KST `daily.yml`이 `scrape_daily.py`(수집) 후 `trend/curate_news.py`(선별: 글로벌 ≤6, 한국 ≤5, 기준 점수 미달 제외)를 실행해 갱신. 날짜별 아카이브는 `trend/data/news/YYYY-MM-DD.json` + `index.json`, 페이지에서 `news.html?d=YYYY-MM-DD`로 열람. 과거 스냅샷으로 재생성: `python trend/curate_news.py --backfill 30`
- 지난 호: `trend/issues/YYYY-MM-DD.html` + `trend/issues/YYYY-MM-DD-marketer.html`, 목록은 `trend/archive.html`
- 조사 키워드: `trend/keywords.json` — `always`(상시)와 `focus`(이번 호 집중 주제)를 수정하면 다음 발행부터 반영
- 디자인: 흰 배경, `trend/style.css` 공통 사용. 본문 Pretendard(jsDelivr CDN), 제목 Noto Serif KR(Google Fonts)

## 편집 원칙
- **메인 메시지:** 기능은 AI가 복제한다. 남는 경쟁력은 **고객의 의도를 파악하고 제품·메시지에 반영하는 일**. 매호 주제는 달라도 결론은 이 관점으로 연결한다.
- **매호 핵심 질문 하나**를 정하고, 네 섹션이 그 질문으로 이어지게 한다: 트렌드에서 질문을 세우고 → 사례로 가능성과 조건을 확인 → 체크리스트로 우리 상황을 판단 → TRY THIS로 작은 결과물을 만든다.
- 독자: 사내 마케팅·기획·제작 실무자 + 광고주 담당자. 같은 본문에서 역할별 결론(.roles: 실무자에게 / 광고주에게)을 따로 준다.
- 읽는 시간 8~12분. 핵심 트렌드 1개·사례 1개·실습 1개를 완성도 있게.

## 발행 절차 (자동 예약 작업이 따르는 규칙)
1. **조사 범위 분리**
   - 뉴스: keywords.json으로 최근 7일. 발표일과 실제 적용 시점 구분.
   - 사례: keywords.json의 `case_search`로 탐색. **최근 1년 이내(가능하면 최근 6개월) 공개된 사례를 우선**하고, 기업 실적 발표·공식 발표의 최신 수치를 쓴다. 그보다 오래된 사례는 본 사례가 아니라 '참고 사례' 한 줄로만 쓰고, 쓸 경우 공개 시점을 밝힌다.
2. **구성 — 두 페이지로 나눠 발행 (탭: 주간 뉴스레터 | 마케터 자료 | 오늘의 AI 뉴스 | 지난 호)**
   - **주간 뉴스레터 (`index.html`)** — 누구나 읽는 트렌드 해설
     - 마스트헤드(히어로 카피 + 키워드 칩) → 3줄 요약(+ 바로가기, 읽는 시간) → EDITOR'S NOTE(핵심 질문, 짧게)
     - **01 핵심 트렌드:** `.frame` 블록(마크업: `<div class="frame"><span class="tag">변화</span><p>본문</p></div>`, 판단은 `<div class="frame judge"><span class="tag a">판단</span><p>…</p></div>`)으로 변화 → 근거 → 마케팅 영향 → 한계 → 판단(실험할 일 / 준비할 일 / 지켜볼 일 / 지금 점검할 일). 고객 의도와 연결되는 신호 1건.
     - **02 두 번째 꼭지:** 그 주의 또 다른 주요 이슈 1건을 같은 `.frame` 구조로(예: 보안·규제·플랫폼 변화).
     - **03 브리프:** 함께 볼 소식 2~3건(`.briefs`) + 플랫폼 정책·기능 변경 `.alert`.
     - 마케터 자료로 가는 `.cta` 박스 → GLOSSARY → 출처.
     - `.frame`을 쓰는 꼭지는 `<section class="framed">`로 감싼다. 들여쓰기는 블록과 블록 사이(첫 블록 뒤~판단 블록 앞)에 낀 표·숫자 박스·문단에만 자동 적용되고, 판단 블록 뒤에 이어지는 소제목·문단이나 블록이 없는 섹션은 왼쪽 끝에서 시작한다(블록이 없는 섹션엔 framed를 붙이지 않는다).
   - **마케터 자료 (`marketer.html`)** — 이번 호 주제를 업무로 옮기는 실무 키트
     - 마스트헤드(키트 제목 + 이번 호 뉴스레터 링크) → '이번 주 키트' 요약(적용 사례 / 적용 판단 / 이번 주 결과물)
     - **01 적용 사례:** 실제 사례 1건. 배지(`.badge.real` / `.badge.vendor` / 재분석 여부) + 사례 카드 표(`.tbl.case`: 기업·시점·출처 / 해결하려던 문제 / 실제 적용 범위 / 드러난 고객 의도 / 작업 방식·사람의 판단 / 결과 / 측정 조건 / 한계) + '우리에게 적용한다면'(가상 예시 표시) + `.roles`.
     - **02 체크리스트:** 사례와 연결된 5~7개. 확인할 것 | 완료 기준 | 권장 담당 + `.verdict`.
     - **03 TRY THIS:** 20~30분 실습. `.spec` → `.steps` → 복사용 프롬프트(확인된 사실/추론 구분) → 완료 기준 → `.roles` → 다음 단계 → 오늘 팀에 던질 질문.
     - GLOSSARY → 출처(이 페이지에서 쓴 것만).
3. **사실·출처 원칙**
   - 브랜드·광고주·대행사 원문 발표와 공식 자료 우선. 솔루션 업체 고객 사례는 '공급사 공개 사례'로 표시.
   - 성과 수치는 비교 기준·측정 기간과 함께. 공개되지 않은 항목은 추정하지 않고 '미공개'. 소재를 많이 만든 것과 매출이 늘어난 것을 구분.
   - 실제 사례 / 가상 예시를 눈에 띄게 구분. 성과 보장 표현 금지. 확인되지 않는 내용은 넣지 않는다.
   - 팩트체크 필수 항목: ① 영어 수치의 한국어 단위 환산(billion = 10억, 600 billion = 6,000억) ② 출간 연도와 수상 연도 구분 ③ 발표 날짜는 2차 보도가 아닌 공식 발표(회사 블로그·보도자료)로 확인 ④ '출시됨'과 '적용 예정' 구분 ⑤ 서비스 제공 지역은 공식 출시 발표 기준 ⑥ 원 보도에 기업 답변이 있으면 '공식 입장 없음'이라 쓰지 않고 답변을 반영 ⑦ 헤드라인만 확인되고 본문을 확인 못 한 사례는 넣지 않는다. ⑧ 수치의 측정 단위를 원문 그대로 쓴다(예: '스캔 101건 평균'을 '공격 1건 비용'으로 바꾸지 않는다). 추정치는 '추산'·'추정 범위'로, 무엇이 빠졌는지 함께 쓴다 ⑨ 재인용 통계는 원 조사까지 거슬러 확인하고 조사 대상·문항 의미를 쓴다(예: 'AI가 가장 효과적이라 평가한 비율'을 '이용률'로 쓰지 않는다) ⑩ '비중 감소'와 '양 감소', '%'와 '%포인트'를 구분한다 ⑪ 피해·대상 범위를 원문보다 좁히거나 넓히지 않는다 ⑫ 서로 다른 시점·OS·지역 비교는 기준을 명시한다 ⑬ 이번 주 자료가 아니면 '같은 주' 같은 제목을 쓰지 않고 '배경 연구'로 표시한다 ⑭ 검증하지 않은 전칭 단정("한 번도 ~된 적 없다")은 쓰지 않는다 ⑮ 편집 관점은 사실처럼 쓰지 않고 관점임을 밝힌다 ⑯ 용어 풀이에서 '무료·누구나'처럼 라이선스 조건을 생략하지 않는다.
4. **표현**
   - 용어 풀이: 비전공자(문과생 마케터)가 모를 기술 용어는 첫 등장 시 <sup class="fn"><a href="#gN" id="rN" title="용어: 풀이">N</a></sup>로 번호를 달고, GLOSSARY(ol.gloss)에 1~2문장 비유 중심 풀이. 번호는 문서 등장 순서.
   - 사족 금지: 뉴스레터 자체를 설명하는 멘트('이번 호부터는~', '~를 목표로 합니다'), 연결용 문장('흥미로운 건~', '여기서 해볼 만한 질문이 있습니다', '~한 셈입니다', '~할 때입니다')을 쓰지 않는다. 문장은 사실이나 판단으로 바로 시작.
5. **발행 전 확인 질문**: 이번 호가 답하는 마케팅 질문이 한 문장으로 정리되는가 / 사례가 실제 적용을 확인할 수 있고 가상 예시와 구분되는가 / 수치 가까이에 근거 링크가 있는가 / 적용 가능·어려운 조건이 드러나는가 / 체크리스트와 실습이 사례에서 자연스럽게 이어지는가 / 실무자와 광고주가 각각 가져갈 결론이 있는가.
6. `index.html`·`marketer.html`을 새 호로 교체하고, `issues/<날짜>.html`·`issues/<날짜>-marketer.html` 사본 생성(링크는 ../, 두 사본끼리의 CTA 링크는 서로를 가리키게). `archive.html`의 ARCHIVE:START 바로 아래에 '뉴스레터 · 마케터 자료' 한 줄 추가 → main에 커밋·푸시 → GitHub Pages 자동 배포.


## 디자인 규칙 (2026-10-20 개편)
- 본문 19px(모바일 18px), 회색 글자는 진하게(#333/#5c5c5c). 작은 글씨도 14.5px 이상.
- 블록 이름표(변화·근거·마케팅 영향·한계·판단)는 본문 위에 두고 위→아래 한 줄로 읽히게 한다. 왼쪽 들여쓰기 칸은 쓰지 않는다.
- 판단 블록은 옅은 배경 박스로 강조해 섹션의 결론이 한눈에 보이게 한다.
- 모든 페이지 탭 오른쪽에 글자 크기 버튼(보통/크게/아주 크게)을 둔다. 새 페이지를 만들 때도 같은 마크업·스크립트를 넣는다.
